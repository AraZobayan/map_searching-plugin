# 决策记录：地铁/公交沿线 POI 地图

> 每定一条追加「结论 + 理由」；未定的放「待定问题」。

## 已确定

### D1｜追问强度：拷打
- 结论：用户选择「拷打」强度，严格挑战前提直到重要未知暴露。
- 理由：用户主动要求压力测试，且项目方向（地图 + POI + 线路）容易想当然。

### D2｜保留决策记录
- 结论：本文件即决策记录，每轮追加。
- 理由：用户选择要文件记录，便于日后回看取舍。

### D3｜核心场景：出差/旅行选住处
- 结论：真实用途是「沿某条线找酒店，要求离站点近、周边有超市和吃的」。
- 理由：用户自述；这决定了产品价值是「筛选与比较」，而不只是「把线画出来」。

### D4｜差异点：A→B 路线上的「沿线资源」，不是「显示线路」
- 结论：高德能给 A→B 的地铁换乘方案，但不告诉你这条方案经过的站周边有什么。产品价值 = 拿这条方案的所有站点，反查每站周边的酒店/按摩/超市，并在同一张图上高亮站点 + 线路 + POI。
- 理由：用户原话场景——B 地住宿紧张且不想住太远，于是沿通勤线找住处；或路上临时想按摩，找沿线店铺。这是「路线 × 周边资源」的组合查询，现有地图 App 没有。
- 推论：核心数据流是「起终点 → 规划方案 → 方案经过的站序列 → 逐站 POI 搜索 → 地图叠加」，比「画一条线」重。

### D5｜输入形态：表单式（选线路 + 勾品类），暂定
- 结论：先做表单，不做一句话语义搜索。
- 理由：出差场景意图固定，NLP 解析错误难补救。
- ⚠️ 与 D4 有冲突：D4 的主线是 A→B，表单却是「选一条线」。待 Q1 澄清。

### D6｜覆盖范围：任意城市，靠高德/百度线路 API 动态取数
- 结论：不做单城市硬编码；线路与站点走开放平台接口。
- 理由：用户明确要任意城市。
- 代价：要处理接口配额、线路名歧义（「2号线」在多个城市重名）、换乘方案多解。

### D7｜形态：手机端 App / 小程序，暂定
- 结论：用户选了手机端。
- ⚠️ 待挑战：出差选住处通常发生在出发前、在电脑上比选，手机端可能是错的形态；且移动端 key/主体资质有额外门槛。

### D14｜只做「找」，不做「导航」
- 结论：范围限定在「公交/地铁沿线找店」。步行/驾车导航、实时公交、下单都不做，找到店之后跳高德。
- 理由：用户原话。有车的人不需要刻意找近的，只有坐公共交通的人才在意「出站后步行/骑车多远」，所以只对公交地铁沿线做。这也让产品边界清晰：一个「沿线找店」工具。
- 推论：不需要路径规划里的驾车/骑行，只需要「步行到站的距离估算」和「站到 B 的已知时间」。

### D15｜由 agent 写代码，用户验收
- 结论：agent 建项目、写完整代码、跑通给用户看；用户提供高德 key 和常用城市。
- 理由：用户选择。

## 重要风险（待解）

### R1｜个人开发者搜索配额极低，可能直接打穿方案
- 事实：高德 JS API 流量限制表与 2022 年搜索接口配额公告一致——**个人认证开发者的「周边搜索」为 100 次/日级别**，企业认证 1000+/日（[流量限制说明](https://developer.amap.com/api/javascript-api-v2/flowlevel)、[配额调整公告](https://lbs.amap.com/news/search-interface-adjustment/)）。
- 影响：一次 A→B 查 8 个站 = 8 次调用（多品类合并成一个 keywords/`types` 请求时）或 32 次（分品类查）。100 次/日 ≈ 每天只能查 3～12 次，无法「日常替代」。
- 缓解：① 多关键字用 `|`、多类型用 `types` 合并成单次请求（[搜索 POI 文档](https://developer.amap.com/api/webservice/guide/api-advanced/newpoisearch)）；② POI 结果本地缓存 7～30 天，同一城市第二次查几乎零消耗；③ 只查关键站；④ 必要时企业认证或买流量包。

### R2｜「本地跑」不等于「手机流量能用」
- 事实：本地跑的服务器是用户家电脑，手机走流量时请求到不了它，需要公网 IP 或内网穿透。
- 待定：纯静态 JS API（无后端）／内网穿透／Workers 代理，见下一轮。

### D16｜配额策略：缓存 + 合并请求，先跑起来
- 结论：不急着企业认证。先把多品类合并成单次请求、POI 结果本地缓存（7～30 天），用 100 次/日硬扛自用。
- 理由：自用频率低，真实痛点出现前不值得为配额去办执照。

### D17｜架构：纯静态页 + 高德 JS API
- 结论：前端一个静态页面，`AMap.Transfer`（公交方案）+ `AMap.PlaceSearch`（周边搜索）+ 地图覆盖物全部在浏览器里跑；无后端。
- 理由：手机走流量可直接访问；不需要内网穿透；不需要服务器。代价是安全密钥明文（自用可接受）。
- 注：2021-12-02 后申请的 key 必须配 `securityJsCode`，否则地图加载失败（[安全密钥文档](https://developer.amap.com/api/javascript-api-v2/guide/abc/jscode)）。

### D18｜当前不写代码
- 结论：用户暂无 key 且 token 紧张，本轮只出结论与方案，代码留到下一轮。
- 理由：无 key 无法验证真实数据，此时写码容易返工。

### D19｜候选站：合并所有方案去重
- 结论：不只取第一个方案；把高德返回的全部换乘方案的站合并去重，作为候选站集合。
- 理由：只解析最优方案会漏掉「换乘更少、站更少」或「平行线路」的更好选择，而零额外配额就能覆盖。
- 代价：站数从约 12 涨到 25 左右，靠缓存和「按需加载」控制调用量。

### D20｜不显示价格
- 结论：列表不显示价格、人均、评分，只呈现位置与时间信息（离站距离、到 B 总时间、品类、名称）。
- 理由：人均≠房价，显示会误导；用户接受自己去携程比价。工具定位就是「缩小范围」。

### D21｜主力机 iPhone
- 结论：按 iOS Safari 优先做 PWA。
- 理由：iOS 16.4+ 才支持「添加到桌面」，且部分能力受限；布局要用 `dvh` 而非 `100vh`，避开 Safari 底部工具栏，触摸目标 ≥44px。

### D22｜城市不限，但不支持跨城
- 结论：任何城市都能查，只要起点与终点在同一城市。「常用城市」只是默认值和缓存键，不是白名单。
- 理由：高德公交换乘规划（`AMap.Transfer`）要求 `city` 参数，且官方明确只支持同城规划；跨城要接火车/高铁方案，超出「沿线找店」范围。
- 城市来源：地址输入提示（`AutoComplete`）的结果自带城市与 adcode，自动带出，不需要用户先选城市；定位只用于猜默认城市。
- 代价：换城市首次查询是冷缓存，多花几次配额。

### D23｜JS API 2.0 的 Transfer 返回结构与 1.4 不同（实测）
- 事实：`plan.segments[]` 用 `transit_mode` 区分 WALK / SUBWAY / BUS；折线在 `segment.transit.path`（`[lng,lat]` 数组）；站点只有 `transit.on_station` / `transit.off_station`；**没有 `buslines` 数组**；线路名只能从 `instruction` 文本里抽。
- 理由：用户贴回的实测 JSON。旧解析假设的 `segments[].transit.buslines[]` 在 2.0 里不存在，所以静默返回空数组、0 站 0 线。
- 推论：解析必须基于 `transit_mode` + `transit.path` + `on_station/off_station`。

### D24｜途经站靠 LineSearch 补，每条线路一次
- 结论：Transfer 只给上下车站，沿线的中间站用 `AMap.LineSearch` 按「城市 + 线路名」查整条线路，每线路只查一次并按 `城市+线路名` 缓存在内存。
- 理由：「沿线找店」需要中间站；这是唯一能拿到整条线站序列的接口。配额成本可控（一次 A→B 查询只多几次调用）。
- 代价：线路名要从 `instruction` 里抽，抽错就查不到；查不到时退回只用上下车站，并在调试区写明。

### D25｜路线与站点按「选中方案」呈现，方案可切换（部分推翻 D19）
- 结论：
  - 高德返回 1 个方案 → 自动选中，直接画路线，不显示选择器。
  - 返回多个方案 → 先列出方案（耗时、线路序列、换乘次数、距离），**用户选中一个之后才画路线**；随时可切换。
  - 地图上同一时刻只画一个方案的路线和站点。
- 理由：用户实测反馈——多方案同时画在一张图上分不清哪条是哪条，也无法据此判断住哪。选择器把「看全部」和「看清一条」分开。
- 与 D19 的关系：D19 的初衷是「不漏掉换乘更少或平行线路的方案」。这个目标改由**方案选择器**实现——所有方案都列出来让用户主动切换，而不是靠合并站点。因此候选站改为「选中方案的站」，不再跨方案合并。
- 代价：切换方案后候选站变化，POI 需按新站重查；靠按站点 id 缓存降低重复请求。
- 待定：切换方案后已查到的 POI 是否保留显示（建议保留缓存、按需补查）。

### D26｜分两级：选中方案只画经过段；选中线路查 POI 时才画整条线
- 结论：
  - **未选中方案**：地图上不画任何线路与站点，只画起终点。
  - **选中方案**：只画该方案实际经过的路径段与站点，**不画路径之外的站点**。
  - **选中某条线路、准备查周边 POI 时**：才画出该线路的整条线路与全部站点。
- 理由：用户澄清。方案是「怎么走」，线路是「沿线哪一站值得住」，两者是不同的信息层，混在一起会让人分不清哪些站真的经过。
- 影响：途经站（整条线）的收集与绘制，属于「选线查 POI」流程，不在方案选择流程里触发。
- 与 D25 一致：同一时刻地图上只呈现一个方案。

### D27｜详情卡显示完整 POI 信息（推翻 D20）
- 结论：点店铺后展示详情卡，包含店名、品类、**评分、人均消费、照片（多张）、电话、营业时间、完整地址**、离最近站距离。人均按高德原义展示，**不加「非房价」提示**。
- 理由：用户反馈——看不到具体信息的话，「找」这件事就没有意义，用户仍要切到别的软件重新搜索。而这些字段本来就随 `extensions:'all'` 的搜索请求一起返回，不需要额外请求、不额外耗配额，只是之前没渲染。
- 跳转：详情卡底部提供「在携程搜这家」（深链带店名 + 城市）；高德导航暂不做。另提供「复制店名」兜底，防止深链打不开。
- 仍然拿不到的（任何公开 API 都没有）：酒店房价、空房、房型、真实用户评价正文、团购。产品定位不变：缩小范围 + 一键送达，不做订房比价。

## grill 结论文档

本轮拷打已结束。剩余未知均为实现细节，不再追问。

### D8｜输入主线：A→B 方案，线路只是中间结果
- 结论：核心输入是起点 A、终点 B；调用高德公交换乘规划，取一个方案的站序列，再逐站查周边 POI。
- 理由：用户确认。这解决了「B 住不起/没房，沿线哪站能住」的真实问题。
- 代价：需要处理多方案、换乘段、步行段、公交段。

### D9｜排序依据：到 B 的总时间
- 结论：结果按「酒店→站步行估算 + 该站到 B 的已知时间」排序，离站距离作辅助信息。
- 理由：真实决策变量是通勤总时长，不是直线距离。且该指标几乎不额外消耗配额。

### D10｜沿线范围：关键站优先，按需加载
- 结论：默认查「B 站 + B 前 5 站 + 上下车站/换乘站」，其余站点用户点开再加载。
- 理由：全站 × 全品类会到 60～80 次请求，配额和手机性能都吃不消；而中间站恰恰是住宿需求核心，不能只查上下车站。

### D11｜形态：响应式网页 + PWA，手机优先
- 结论：一份响应式 Web 代码，手机浏览器打开并可「添加到桌面」。
- 理由：个人主体微信小程序无地图组件权限（硬限制），高德 Web 服务 key 不能放前端需后端代理；PWA 无审核、无主体门槛，手机优先成本最低。

### D12｜「附近」：直线筛 + 前几名算步行
- 结论：默认直线 800m 可调，列表显示直线距离；只对用户点开的酒店算真实步行路线。
- 理由：兼顾准确度与接口配额。

### D13｜数据边界：只有 POI，没有房价与空房
- 结论：产品定位为「缩小搜索范围的工具」，不做订房。
- 理由：高德/百度 POI 接口无实时库存与房价；携程/美团无公开 API。用户已接受此边界。
